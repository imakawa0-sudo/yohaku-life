## 初回移行の構成

制作ファイルは元のフォルダ構成で保存する。公開57までの59コミットは、完全な履歴を収めた `history/sites-v57.bundle` に保持する。GitHubの画面に並ぶ移行後のコミット履歴と、バックアップ内の元の59コミットは区別する。

元の公開57を履歴付きで取り出す場合は、リポジトリのルートから次を実行する。

```bash
git clone --branch main history/sites-v57.bundle ../yohaku-sites-v57
```

取り出した履歴の先頭は `a0c36bbbafa278e065836b9a6a4f636fe75089e3`、コミット数は59になる。通常の継続開発は、このGitHubリポジトリの `main` を基準に行う。バックアップから取り出した別履歴をGitHubの `main` へ強制送信しない。

## 開発を続けるとき

1. `AGENTS.md`、`docs/DESIGN.md`、`docs/ROADMAP.md` と最新のユーザー依頼を確認する。
2. GitHubプラグインで保存先と `main` の最新コミットを確認し、その内容を作業の基準にする。別の作業による更新がある場合は、内容を確認して統合する。初回復元時のローカル履歴と、GitHubの `main` は区別する。
3. 依頼された実装と、その変更に必要な検証を行う。ゲームの動作・見た目を変更した場合は、既存の実試遊方針に従う。
4. GitHubプラグインを優先し、追加・変更・削除したファイルだけを反映する。関連する変更は1つのコミットにまとめ、変更していないファイルや `history/sites-v57.bundle` を毎回送り直さない。通常の作業では強制送信や履歴の削除を行わない。
5. 保存前に確認したGitHubの最新コミットにつながる形で `main` を更新する。途中で別の更新が入った場合は、その内容を取り込んでから保存する。保存後はGitHub側のコミットと対象ファイルを確認し、保存先と保存した版をユーザーへ報告する。

複数ファイルを変更するときは、GitHub側の最新のファイル構成を引き継いで、変更分をまとめたコミットを作る。保存直前にもブランチの先頭が想定どおりか確認し、他の更新を上書きしない。クラウドブラウザからのアップロードは通常の保存手順には使わず、プラグインで保存できない場合に別の認証済みの方法を検討する。保存できなければ変更を保持し、未完了であることを報告する。

GitHubへ保存するのはソースコード、画像、テスト、設計・開発資料などの制作データ。依存パッケージは `package-lock.json` を使って復元し、`node_modules/` は保存しない。ビルド成果物は `npm run build` で生成できる。ユーザー個人のゲーム内セーブや認証情報は制作データと別に扱う。

## Sitesとの関係

現在の配信先は `https://yohaku-life-together.nuttystoat18.chatgpt.site`。GitHubへの保存だけで新しい公開版を配信しない。Sitesへの公開が依頼された場合は、公開するコミットを確認し、Sites側の手順でビルド・公開・公開後の確認を行う。

Sitesの専用ヘルパーが管理する作業場所と、GitHub用の作業場所を区別する。送信コマンドの宛先を省略した場合にSitesへ誤送信しないよう、リモートを確認する。
