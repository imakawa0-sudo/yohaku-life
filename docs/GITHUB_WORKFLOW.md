## 開発を続けるとき

1. 最新のユーザー依頼、`AGENTS.md`、`docs/DEVELOPMENT_HANDOFF.md`、関係する設計とロードマップを確認する。
2. GitHubプラグインで保存先と `main` の最新コミットを確認し、その内容を基に作業ブランチを作る。別の作業による更新は内容を確認して統合する。初回復元時のローカル履歴とGitHub mainの履歴を区別する。
3. 依頼された実装と必要な検証を行い、関連文書を同じ変更単位で更新する。ゲームの動作・見た目を変更した場合は、最新HTMLで実試遊する。文書のみなら内容・対象版・リンク・差分を確認し、ゲームの再試験を形式的に繰り返さない。
4. 変更ファイルだけを作業ブランチへ保存し、mainを対象にPRを作る。[PRの記入項目](../.github/pull_request_template.md)に従って、目的・結果・確認範囲を示す。変更していないファイルや `history/sites-v57.bundle` を送り直さず、強制送信や履歴の削除を行わない。
5. 開発側のレビューと必要な検証を終え、Docs7のPR Reviewの実行状態・指摘を確認する。Hosting OFFでは対象文書を含む最後のPR更新から5分後が開始条件。結果がまだない場合は時間を置いて確認し、対象外・利用枠・未実行なら、その状態と独立した確認結果をPRに残す。設定ONやコメントがないことだけを合格としない。[Docs7の条件と役割](CONTEXT7_DOCS7_WORKFLOW.md)
6. mainとPR先頭が想定どおりか再確認し、関連する変更をまとめて統合する。PRの期待する先頭SHAを指定して他の更新の取りこぼしを防ぐ。統合後はmainのコミットと対象ファイル、その他の既存ファイルの保持を確認し、PRと保存した版を報告する。
7. Code Watchのマージ後の提案を確認する。文書変更が不要ならPRが出ない場合もある。文書のみの変更など公式の対象外を実行失敗と混同しない。提案の自動採用はせず、根拠・対象版・差分を確認する。Notionの進捗・引き継ぎも実際の保存版へ結び付ける。

複数ファイルを変更するときは、GitHub側の最新のファイル構成を引き継いで、変更分をまとめたコミットを作る。保存直前にもブランチの先頭が想定どおりか確認し、他の更新を上書きしない。クラウドブラウザからのアップロードは通常の保存手順には使わず、プラグインで保存できない場合に別の認証済みの方法を検討する。保存できなければ変更を保持し、未完了であることを報告する。

GitHubへ保存するのはソースコード、画像、テスト、設計・開発資料などの制作データ。依存パッケージは `package-lock.json` を使って復元し、`node_modules/` は保存しない。ビルド成果物は `npm run build` で生成できる。ユーザー個人のゲーム内セーブや認証情報は制作データと別に扱う。
