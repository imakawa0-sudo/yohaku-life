# 住居H1-Bで具体化した判断

2026-11-23（台湾）。実装担当が今回の工程を進めるために具体化した内容を、判断した順に残す。ユーザーが個々の内部仕様を指定したという記録ではない。The Sims 4・Kenshi・RimWorldとテキストシミュレーションから学び、生活・建築・仲間・生産・冒険が結び付く完成像を前提とする。現在の名称、画風、人数、拠点数、画面構成を完成形の上限にはしない。

| 順  | 判断と理由                                                                                                                                                                                                       | 後から変更する場合の影響                                                                                                                           |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 前回提示したH1-Bの最初の統合を続け、実装・検証・通常のGitHub保存・Notion更新まで進める。継続依頼と既存の保存方針に含まれるため、作業途中の再承認は挟まない。Sites本番の公開は含めない。                          | 認識が違っていた場合は、確認できる差分と通常の追加コミットで修正する。                                                                             |
| 2   | H1-Aで分離済みの作業場所を使い、H1-B用の別ブランチで開発する。H1-Aの成果と元の作業場所を保つ。                                                                                                                   | 作業場所を変える場合の影響は、ローカルの準備と移動に限られる。                                                                                     |
| 3   | 新しい自宅指示だけを空間処理へ接続し、旧行動の残り時間・総時間・予約材料はそのまま継続する。旧保存は新方式を理解しないため、保存キーと包みをv2に分け、新方式へは明示した分岐で移る。                             | 互換処理が増える。すべてを即時変換する方式へ変えるなら、旧進捗を推定しない別の移行契約が必要になる。                                               |
| 4   | 家具のマスは通り抜けず、安定した隣接床を利用位置にする。室内1マスは1分、部屋間通路は3分、扉は通行可否を担う。旧行動の時間は変えない。                                                                            | 移動のバランスと新保存の継続条件に関わる。扉の時間や利用位置の方式を変える際は、保存互換性も検討する。                                             |
| 5   | 自宅での新しい組行動は実際の同地点を前提にし、共食は実際に利用時間が重なった記録から各自へ一回ずつ加点する。地域をまたぐ組行動・運搬と全面的な自動接近は後続に接続する。                                         | 複数人行動の全面統合では、この参加条件と時間の契約を拡張する必要がある。今回の範囲をH1全体の完成とはしない。                                       |
| 6   | 新しい地域移動は、既知の自宅出発地点を履歴として保存する。途中取消ではその地点へ戻る現行の互換規則を守り、実際に自宅へ到着した時点で居間の入口を確定する。旧保存で不明な出発地点は推定しない。                   | 地域移動そのものを連続した空間処理へ移す際には、この履歴と取消の復帰規則を移行する必要がある。                                                     |
| 7   | 部屋の許可を外した場合、新しい入室と設備利用を止める。すでに室内にいる住民は歩いて退室でき、退出後の再入室はできない。管理操作だけで住民を閉じ込めないための規則。                                               | 将来の侵入・警備・避難では、退出だけに使える経路など、より細かな規則が必要になる可能性がある。                                                     |
| 8   | 当初、旧設備作業中は、編集前後で計算した部屋間の保護経路が同じであることを求めた。旧保存に実際の経路履歴がないための保守的な案だった。**レビュー後、次項の方式へ修正した。**                                     | この案では近道を追加しただけでも拒否する場合があり、建築の自由度を不必要に狭めると分かった。                                                       |
| 9   | 旧方式から分岐するときに、旧設備作業の依存先を守るための通路列を保存する。この列は過去の実経路の復元ではない。列を保った近道の追加は許し、保存し直しても保護先は変えず、旧作業の完了・取消・成功した置換で除く。 | 小さな互換用の保存情報と、検証・後片付けが増える。旧作業の契約を変える場合は、この記録の扱いも変える必要がある。                                   |
| 10  | 保存直前の比較に加え、対応ブラウザではWeb Locksで新版のタブの保存順をそろえる。現行のWeb Storage仕様では読取りと書込みを一体にした排他が保証されないため。APIのない環境では比較処理と同時操作の制限案内を残す。  | 保存完了を待つ処理と、待っている間の操作の扱いが増える。保護の対象は協調する新版タブで、旧コードや外部の保存編集を止めるものではない。             |
| 11  | 社交設備では、本人が利用を1分消費し、相手がその1分の始めと終わりに同じ地点にいた場合だけ同席ありと記録する。指示時の相手の場所や文章だけで会話を確定しない。旧の非空間Taskは従来どおり継続する。                 | 現在保存するのは同席の有無。将来、会話時間や参加割合で効果を変える際は観測時間と保存互換の追加が必要になる。                                       |
| 12  | 旧作業の設備席等を忠実に変換できないときは、原本を修正せず住居方式への分岐だけを理由付きで拒否する。書込み候補の検証も書込み前に行い、他の枠を守る。                                                             | 一部の旧保存はそのままでは新方式へ移れない。旧方式を続けられるようにし、将来の変換範囲拡張には進捗・材料・最初の朝を守る明示的な規則が必要になる。 |

根拠となる比較研究は [reference-check.md](reference-check.md)、実装契約は [H1-B設計](../../superpowers/specs/2026-11-23-housing-h1b-design.md) に分けて記録する。参考作品の規則と、本作のために選んだ規則を混同しない。
