## 1. 結論と判断の保留範囲

**優先して試す具体案はC。ただし、A/B/Cを同じ行動で比較した後に採否を決める。** Cの意味は「全機能を三重に実装する」ことではない。地域・敷地・建物という所属関係を持ち、庭から屋内まで連続した位置関係が必要な範囲には一つの局所マスを置き、離れた範囲を出入口・道でつなぐ構成である。部屋ごとに別世界へ切り替える必要はない。

所属の階層、経路を求める仕組み、画面の表示方法は別にする。Bでも建物や敷地のIDは持てるし、Aでも地図は描ける。マス方式が細かな手操作を必須にするわけでもない。今回の比較対象は、主に「移動可能な位置と、その間を通る条件を何で表すか」である。

現行コードから強く言えるのは、**どの案でも、現在位置と行き先、移動と利用、通行可能と通行許可、予約と実占有を分けなければ、5行動を一貫して扱えない**こと。現在の経路関数だけを置き換えても解決しない。

## 3. 比較する三案の具体的な構成

### A：部屋・地点と接続を拡張する

室、庭、階段踊り場、門、家具の利用位置などをノードとして置き、通れる接続に時間・幅・開閉・施錠・通行権を持たせる。室内の重要な障害物で通路が変わる場所だけ中間ノードを追加する。現在の室内マスを配置用に残す場合も、実際の通行判定をマスとグラフのどちらが決めるかを明示する。

強みは、テキストで場所を選ぶ操作、物資の所在、複数階、遠方拠点を少ない場所情報で扱えること。弱みは、自由に動かした家具や壁が作る通路を、接続へ変換する規則が別途必要なこと。ノードに「通路幅2」と書くだけでは、途中の曲がり角を大きな家具が通れるとは限らない。

### B：地域内の連続マスを正本にする

地域ごとに連続した床・地形・壁・戸口・占有マスを持ち、庭・道路・建物内の人物と物を同じ座標系に置く。階はzまたは階層ごとの平面と階段接続で表す。部屋は地形から求める領域、またはその上へ付ける用途・権利の範囲になる。地域をまたぐ長旅は、別途の地域接続で扱える。

強みは、家具・通路・屋外への迂回・工事による遮断が同じ空間の変化になること。弱みは、実際に扱う地形・区画・建物の位置を初期から決める必要と、旧部屋グラフを連続座標に変換する難しさ。Bが世界全土を毎分全マス更新する方式だとは決めつけない。領域分割・必要時の読み込み・粗い経路探索はBでも可能であり、性能は計測前に断定しない。

### C：所属の階層と、必要な範囲の局所マス・接続を組み合わせる

地域→敷地→建物→階/空間というID参照を持つ。そのうえで、細かな位置関係が行動を変える範囲に局所マスを置く。例えば一つの敷地は、庭・二棟の建物・門まで同じ局所マスにできる。遠くの敷地は道路接続でつなぐ。出入口は「両端がどの位置につながるか」を持ち、経路は局所歩行と接続通過を連結した一つの行程として表す。

強みは、自由な間取りと複数拠点の所在を両立し、旧部屋ごとのマスも互換領域として取り込めること。弱みは、領域をまたぐ境界で距離・時間・権利・予約が二重になったり、姿が消えたりしやすいこと。**同じ家を細分化しすぎないこと、境界を越えても人物・物のIDと時計を一つに保つことが成立条件**になる。

## 5. 暫定推奨の成立条件と撤回条件

Cを優先検証する理由は、自由な家具配置・建築が行動へ返る範囲にはマスが役立ち、複数拠点や遠征の全行程を同じ密度で描く必然は今の目標からは確認できないため。ただし、これは性能実測や試遊による採用決定ではない。

- **Aへ寄せる条件**：同じ試遊で、部屋/戸/利用位置の関係だけで重要な判断が足り、家具の細かな迂回や身体の位置を理解する負担の方が大きい。自由編集から接続を安定して生成できる。こうなればマスの適用範囲をさらに絞る価値がある。
- **Bへ寄せる条件**：庭・道路・隣家・戦闘・救助が連続して起こり、Cの境界処理が例外だらけになる。または見ている範囲を切り替えることで、同じ行動の到着時刻・危険・物資所在が変わる問題が収束しない。この場合は、少なくとも関係する地域全体を連続マスへ統合する。
- **Cの分割を撤回する条件**：局所領域をまたぐたびに別予約や不自然な待機が必要となり、普通の生活で境界の都合が見える。敷地や隣接建物を同一領域へまとめる。階層を維持することと、細かく空間を分割することは同義ではない。
- **全案を見直す条件**：選択できる経路や許可状態は正しいのに、テキスト表示から「なぜそこに行けないか」が読めない、または指示回数が人数/物の個数に比例して増えすぎる。経路の方式だけでなく、対象指定・作業委任・理由表示も同じ試遊で見直す。

速度・メモリ・同時人数の数値は今回のソース読取りからは決めない。後で同じ代表条件・同じ端末・同じ操作を測り、実際の問題に対して範囲分割やキャッシュを選ぶ。

## 7. 旧保存を壊さない増分

### 第1増分：本体に触れず、空間契約だけ比較する

別の実験ディレクトリで、同じ5行動に対してA/B/Cの経路アダプターを作る。本体のGame・House・Libraryは変更しない。試験用の人数・部屋数は比較を読みやすくするための固定条件であり、将来上限ではない。実験には既存の`node:test`と`node:assert/strict`を使い、新しい試験ライブラリは追加しない。

### 第2増分：読み込み境界と保存往復を先に分離する

`isGameV1`/`isHouseV1`は旧条件をそのまま検証する。新しいGameV2/保存EnvelopeV2/LibraryV2の検証と、純粋な`migrateV1`を別に置く。旧ゲームを原文のまま保護し、移行の成果を一度に保存する。gameとoriginの両方が検証・変換・再検証を通ってから一つのslotとして確定する。一方だけ成功した保存で元slotを上書きしない。

移行は時刻・乱数・人物の外見選択・技能・関係・記憶・荷物・設備ID・途中時間・予約量を不用意に変えない。変換したことを「その世界で引越や改築が行われた」とする出来事へ変えない。開始分岐は移行後origin、途中分岐は移行後gameを複製する。import時のslotの新ID付与と、世界内の人物/家具/場所IDの保持は別にする。

新旧キーを分ける案では、旧タブが旧保存を更新した後の再移行を自動上書きにしない。元データの識別と移行済み情報を持ち、異なる継続として扱う必要がある。同じキーを変換する案では、旧版タブによる書込みと形式不一致を扱う必要がある。どちらも`ReformApp.save`の現在の競合保護を飛ばさない。

### 第3増分：家と配置を互換領域へ包む

旧部屋は幅4・元の高さ・元のwalls/doors/fixture.cellを保持する。座標へ写す場合は `x=cell%4, y=floor(cell/4)` とする。部屋幅を先に変えて同じcell番号を解釈すると家具が別位置になるため不可。

旧linksは、旧部屋の入口0同士をつなぐ互換接続へ写す。任意の部屋グラフには平面上で無理なく隣接配置できる保証がないので、旧室を適当な一枚の地図へ並べて「元の家」と称さない。旧doorsは室内の通過マスであり、linksの扉へ勝手に割り当てない。元の配置や距離を変えずに新しい自由形状の家も作れるよう、旧形式と新形式の空間を区別する。

### 第4増分：途中Taskの互換処理と新行動を分ける

旧Taskのtotal/remainingには移動と利用の内訳がない。そこで、途中Taskを新しい行程へ比例配分して「既に到着した」と推定する移行はしない。

推奨候補は、**旧途中Taskを有限の互換行動として残し、残り時間・予約・partner/followerを保持したまま完了または明示取消まで扱う**こと。新しく始める行動から段階式にする。旧途中行動を新しい空間変更と混ぜる場合には、関係する設備/空間の変更を一時待機させるか、旧互換世界として完了させるかを明示的に選ぶ。旧行動の経路が保存されていないのに、現在の家から推定した新経路で無言に完了時刻を変えない。

「旧保存の継続が可能」「残り時間と資源が保たれる」「旧ルールの未来結果まで完全一致する」は別の約束である。特に現在の共食・会話の即時同室化を直す場合は、旧ルールの未来結果まで完全一致するとは同時に約束できない。厳密な旧継続はV1互換分岐で残せる。V2へ移行する場合は、到着不明の旧途中Taskを新ルールの実参加証拠にしない方針を明記し、変更する社会効果を無言で互換保証に含めない。

旧roomしか分からない人物は「旧室内の詳細位置未確定」として受け入れる。新しい経路を初めて始める際に入口0を基準とするなら、それは移行既定値として説明し、保存以前にそこを歩いた履歴を作らない。

### 第5増分：在庫と建築を接続する

現行のGame在庫は一つの初期共有収納へ、cargoは各人物の携行収納へ対応づける。旧Task.reservedは既に差し引かれている量なので、移行時にもう一度在庫から引かない。予約元は旧location/fromとhomeの一致から判定できる範囲で対応づける。新規の仕事ではsource containerを保存し、持ち出した後は現物所在から返却/仮置きを決める。

家具運搬は同じFixture IDの所在を「設置中→運搬中→設置済み」と移す。別IDの家具を作って元を消す手順は、予約や個人割当が切れやすい。工事は最初から全建材を用意せず、まず一種類の通路変更について、計画・材料予約・搬入・施工・中断・保存・完了を通す。今の`ReformApp.build`の木材引落しと、新しいWorkOrderの材料引落しを同時に走らせない。

## 8. 最初の試作に必要な範囲と、後に回せる範囲

### 比較試作に必要

- 三案で同じ人物・場所・家具・戸・許可・資材を参照する小さな設定。
- 現在位置と行き先、移動中と到着後を分ける状態。
- `route`、通行条件の再確認、許可判定、予約判定の独立した入口。
- 戸の変更、工事による短経路の閉鎖、代替経路、完全な通行不能。
- 家具と負傷者を一つのIDで運ぶこと。到着前には設置・治療・会話を完了させないこと。
- 途中保存/再読込と、同じ指示列から同じ状態になること。
- 失敗理由を「物理的に塞がれている」「入室許可がない」「利用枠が予約済み」へ区別すること。
- 本体へ導入する前の旧保存標本：途中料理、途中食事、途中移動、途中救助、家具増設後、開始時originと進行中gameが異なるもの。

### 契約だけ置き、初回の機能完成を待たなくてよい

多層階の自由建築、全家具の寸法/回転、持ち方や共同運搬の細かな動作、賃貸契約、相続、全住環境、温度/音/光の物理伝播、多数NPCの全行動、全勢力の権利、地域全域の最適化、最終アート、最終タブ構成。

ただし複数階・共同施設・二拠点については、最初からID参照と経路の接続例を一つずつ書く。最初の一軒だけの実装を最終形と取り違えず、「二拠点目を足すとGame直下に第二のwoodを増やすしかない」といった構造を避ける。

## 9. 判定可能な受入例

これらは点数の合計で採否を決めるための表ではない。失敗した場合、どの行動条件を満たせなかったかが分かるようにする。

| ID | 操作・条件 | 合格と判断できる結果 |
| --- | --- | --- |
| T1 | Pが離れた設備Fの利用を指示 | 指示直後の時刻と現在位置は変わらず、行き先だけが決まる。移動が完了する前はFの使用効果も同席効果もない。 |
| T2 | T1の移動途中に保存して再読込 | 現在位置/区間、残り時間、対象ID、予約が復元され、未保存継続と同じ時刻に同じ結果になる。 |
| T3 | Pが私室へ向かう途中、短経路の戸へ閉鎖要求 | 未進入の区間には入らない。既に進入している区間は残り時間で終点へ進み、閉鎖要求はその退出を待つ。次の進入では通行権のある代替経路を選び、なければ到達済み地点で待つ。未到着の使用効果は出ない。 |
| T4 | 私室の戸は開いているがPの入室許可がない | 物理的な経路の存在と入室不可を別々に返す。「道がない」とは表示しない。許可後も新たな時間進行前に室内へ現れない。 |
| T5 | 許可を得て進行中、入室許可取消 | 各区間への進入前に再確認し、許可がなければ進入しない。進入済み区間の許可は途中で取り消さず、その区間の残り時間で終点へ進む。次の区間は新しい許可状態で再判定する。既に室内にいる者を外へ瞬間移動させない。退室規則は別にする。 |
| T6 | 家具Fを倉庫から私室へ運び、搬送中に中断 | Fの世界内実体は常に一つ。元の部屋と搬送先へ同時に置かれない。中断後の保持/仮置き位置を取得できる。 |
| T7 | 家具は通常の戸を通れず、広い戸の迂回は通れる | 徒歩経路をそのまま家具運搬へ採用せず、荷の条件を含めて代替を選ぶ。大きさや向きを初回で省く場合は、この例の対象範囲も明示する。 |
| T8 | 工事を計画し、工事開始時だけ廊下を塞ぐ | 計画しただけでは通路を塞がない。工事開始後は通行判定が変わり、既に向かっていた人にも反映される。 |
| T9 | 工事を中断/取消し、その操作を再度実行 | 未消費材料だけが規則どおり残る/返る。同じ材料が二重に返らず、完了結果も二重に生じない。 |
| T10 | Pが私室のQを訪問する | Pは戸口へ到着してから応答を待つ。Qが不在なら会話を始めない。QをPの部屋へ即時移動させない。 |
| T11 | Pが負傷者Rの搬送を指示 | PがRの位置へ着く前にRが動かない。運搬開始後はRの所在が運搬者と矛盾せず、搬送先へ着く前に寝床の利用を完了しない。 |
| T12 | 搬送途中の戸を閉じ、Pが中断 | Rを通行不能な先へ転送しない。保持か安全な仮置きのいずれかを取得でき、Rの重複・消失がない。 |
| T13 | 同じFの同じ利用枠へ二人が予約 | 二重占有を拒否し、別枠/別設備/待機を選べる。所有者だからという理由で予約済み枠を上書きしない。 |
| T14 | 同じ食事場所を予定しているが一人は移動中 | 到着済みで実際に食事へ参加している時間が重なるまで、共食効果を付けない。 |
| T15 | 自宅Aの材料を使って遠い拠点Bの工事を指示 | Bに材料がなければ搬送待ちになる。AにあるだけでBの施工済み材料へ直接変わらない。 |
| T16 | 階段を含む搬送行程で保存/再開 | 階の切替によって人物/物が複製されず、階段の両端と残り時間を保つ。 |
| M1 | 幅4、壁/扉/家具を持つ旧保存を変換 | 全家具IDと元の座標関係が一致し、任意linksを平面化するために家具や室順を移動していない。 |
| M2 | 予約済み料理を残り時間途中で変換 | 在庫の再引落しがなく、残り時間と予約量が保持される。取消・再取消で資材が二重に戻らない。 |
| M3 | gameとoriginが異なる旧slotを変換 | 両方がそれぞれ変換され、開始分岐と途中分岐を混同しない。分岐先の変更が元slotへ漏れない。 |
| M4 | gameだけ正常、originが破損した保存 | 不完全な移行を確定せず、原保存が保護される。 |
| M5 | 変換済み保存を再読込/再書出し | 再移行・再消費・完了の再発火がなく、同じ進行へ戻る。 |
| M6 | 二つのタブで古い状態と新しい状態を保存 | 古い側が新しい進行を無言で上書きしない。移行前後が異なる継続なら、その区別が分かる。 |

最初の小実験ではT1〜T5を中心に、到着・経路再評価・許可の境界を先に確かめられる。5行動全体の本体実装済みや、全受入条件の通過と取り違えない。

## 補記：本体から独立した最小実験

比較を具体化するため、`docs/research/housing-h0-h1-2026-11-23/spatial-probe.ts`と`spatial-probe.test.ts`の2ファイルを新規作成した。本体からも本体へもimportせず、既存ゲームのテスト・package・ビルド設定は変更していない。

Aは場所と接続の列挙、Bは道路を含む一地域の隣接マスからの接続生成、Cは二つの局所マスと道路接続で、同じ名前の地点と同じ移動時間を扱う。Cの地域/敷地/建物/階の所属情報は経路領域とは独立している。Bで道路上のマスが詳細に表れる一方、A/Cはその区間を6分の接続として保持する。

初回は試験先行で未作成モジュールへのimportが失敗した。これは実装前の失敗記録であり、挙動の不具合を実際に検出した証拠ではない。初版の実装後は共通の11条件を三表現で検証した。その後、設計との独立した照合で区間途中の閉鎖/許可取消の規則と設計6.2の不一致を確認したため、進入前と進入後を別の試験に分け、12条件×三表現へ修正した。入室許可に加え、家具を持ち出す許可を別に確認する。予約を得ても引取り前に持出し許可が取り消されれば待機する。結果と正確なコマンドは[検証記録](verification.md)にまとめた。

この実験で確かめるのは、到着・経路変更・許可・所在・保存を分離する共通契約の表現可能性である。A/B/Cの優劣、最終採用、性能、UIの理解しやすさ、既存ゲームへの統合を証明しない。家具は大きさを持たない点として扱い、扉幅・曲がり角・階段搬送・共同運搬・建築材料消費・私室での応答/会話・設備の利用枠・旧保存移行は未実装。最新の区間規則は、進入時の通行許可で現在区間を残り時間どおりに完了し、閉鎖要求/許可取消を次の進入から適用する。閉じた障害物をすり抜ける扱いではなく、占有中の区間の退出を閉鎖要求が待つ抽象化である。構造を削除するAPIは試作にないため、占有中区間の削除や完成壁への置換を待たせる機能は未実装・未検証。途中反転や衝突回避も試していない。
