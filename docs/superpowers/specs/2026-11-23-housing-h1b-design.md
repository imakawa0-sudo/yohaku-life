作成日：2026-11-23（台湾）。基準：GitHub main `a8e6a6b387658253c636e57689acb67fa179e1e8`、対応するローカルHEAD `c070bffcb38379b460d022f33fcb618a6a8c3a89`。

## 目的と今回の完成範囲

H1-Aの空間処理を、実際の住居内の移動、生活設備、料理、待機・取消、画面表示、保存継続へ接続する。新しく作る暮らしと、原本を残して新方式へ分岐した暮らしで、一連の操作を試遊できることが今回の完了条件。

The Sims 4・Kenshi・RimWorldとテキストシミュレーションから学び、生活・仲間・生産・建築・冒険を結び付ける完成像を維持する。現在の名称、画風、人数、拠点数、4タブ、1分の刻みを完成形の上限にしない。

今回の実装判断は開発担当の具体化であり、ユーザーが個々の内部表現を選択したという記録ではない。前回提示した次工程に対する「続きをお願いします」を受けて、実装・確認・GitHub/Notion保存まで進める。

## 比較した方式

1. 全Taskを直ちに段階へ変換：旧remainingから移動と利用を推定することになり、既存の時間・材料を壊す。採用しない。
2. 画面だけに独立試作を追加：本体の時計・材料・保存との一致が確かめられない。採用しない。
3. **既存Gameに住居runtimeを加え、新指示だけ段階式へ接続する。旧Taskは旧規則で完了・取消する。** 今回採用。新しい保存の包みとキーを使い、元の保存と分岐元を保護する。

## Global Constraints

- 既存の人物作成10項目41選択値と外見を保持する。依存パッケージを更新しない。
- ゲームの時計を進める入口は既存 `advance` 一つ。指示・照会・表示・保存・通路設定で時間、乱数、完成効果を進めない。
- 一回のゲーム1分につき `advanceSpatial(state, 1)` を全体で一回だけ呼ぶ。結び付けたTaskを旧remainingでも二重進行しない。
- Taskが材料予約・返却・ゲーム効果を持ち、SpatialOrderが位置・利用残時間・待機・取消段階を持つ。完了と取消を混同しない。
- 旧Taskのremaining/total/reservedを推定分解・再引落ししない。元の旧保存キーと分岐元Slotを変更しない。game/originは独立に検証・複製する。
- 室内位置が不明な旧人物は未確定のまま保持する。次に受理する住居内の新指示で現在の部屋の入口0を初期位置にする規則を画面で説明する。無効な指示では初期化しない。
- 入室・設備利用の許可不足と物理的な経路不通を、判定と日本語表示で区別する。
- 家具のマスを通り抜けない。予約された設備・利用位置、人物の現在マス・着地マス、進入済み接続を壊す編集は材料を使う前に拒否し、理由を示す。
- 別タブ競合、不正保存、保存不可を区別し、保存原本を黙って上書きしない。保存の副作用をReactのstate updaterへ入れない。
- 実装後に最終HTMLをビルドし、実操作・PC/320/390pxの収まり・保存再開を確認する。未実施や代替経路を明記する。
- GitHubは既存mainの子コミットとして変更ファイルだけ保存し、読み戻す。Sites本番は公開しない。

## 1. 住居を空間へ対応させる

`src/reform/housing/` に、型、間取りの対応、runtimeと検証、表示の補助を分ける。既存H1-Aの公開契約は維持する。

- 各部屋をgrid domainにする。壁と家具マスをblockedCellsに含める。
- 家具の使用位置は、隣接する床のうち入口0から到達できる最短のマス、同距離ならcell番号の小さい方。候補がなければその設備は利用不可。入口へ黙って代用しない。
- 座席ごとに別slotを作る。複数席が同じ使用位置を共有することは許す。人物衝突・床の定員は後続の仕組み。
- 部屋間linksは入口0同士、3分。部屋内は1マス1分。新方式の戸は通行可否を持ち、旧方式の戸の追加1分は移植しない。旧Taskの時間は変更しない。
- 室内の戸は、そのマスに接する全歩行辺をgateにする。閉鎖中の戸を別方向から抜けられないこと。室内の戸を部屋間linkの戸だと解釈しない。
- domain/link/door/slotはJSON配列から作る安定したIDを使う。新IDを `#` で分解して家具を推測しない。
- runtime.controlsに閉じたlink、閉じたdoor、部屋ごとの許可人物を保持し、geometryと照合する。これは通行・設備利用の設定で、法的所有や心理的同意ではない。

## 2. 状態と公開インターフェース

`Game.version`は1のまま `housing?: HousingRuntime` を加える。新形式の保存の包みが旧クライアントによる誤実行を防ぐ。`Task.spatial?: HousingTaskBinding` を加える。

```ts
type HousingTaskBinding = {
  orderId: string;
  kind: "move" | "use";
  mealPartners?: Record<string, number>;
  socialCompany?: true;
};
type HousingRuntime = {
  version: 1;
  state: SpatialState;
  legacyStationPaths: Record<string, string[]>;
  unlocated: Record<
    string,
    {
      location: string;
      room: string;
      reason: "legacy-unspecified" | "outside" | "regional-travel";
      departurePoint?: SpatialPoint;
    }
  >;
  controls: {
    closedLinks: string[];
    closedDoors: string[];
    roomAccess: Record<string, string[] | null>;
  };
};
```

人物IDはstate.actorsとunlocatedのどちらか一方に存在する。外にいる人物・地域移動中はunlocatedで、そのlocation/roomと理由を保持する。この段階では地域間移動・野外行動は従来の処理を継続する。新規作成時に家にいる人物は居間の入口0から始める。旧分岐の人物は全員、正確な室内位置を捏造しない。

既知の自宅マスから地域移動を開始する場合、unlocated.departurePointに出発時の地点を履歴として保持する。これは現在位置ではない。到着前の取消ではこの地点へ戻す現行互換規則とし、途中保存でも保持する。その間は復帰地点を壁・家具・部屋削除で失わせない。元から位置が未確定の旧移動は取消後も未確定。地域移動・帰還・救助が家へ実際に到着した時点では居間の入口0を新しい現在位置にする。外への到着で履歴地点を破棄する。

基礎API（詳細型は各ファイルでexportする）：

- `buildHousingTopology(house: House, actorIds: string[], controls?: HousingControls, positions?: Record<string, SpatialActor>): HousingTopology`
- `housingPoint(roomId: string, cell: number): SpatialPoint`
- `housingRoomId(domainId: string): string | null`
- `createHousingRuntime(game: Game, mode: "new" | "legacy"): HousingRuntime`
- `isHousingRuntime(value: unknown, game: Game): value is HousingRuntime`
- `applyHousingHouseEdit(game: Game, house: House): { game: Game; error?: string }`
- `enableHousing(game: Game, mode: "new" | "legacy"): Game`
- `housingStatus(game: Game, actorId: string): HousingStatus`（現在地・行き先・段階・残り利用時間・待機理由・推定完了時間を返す）
- `nextCompletionMinutes(game: Game): number | null`
- `setHousingPassage(game: Game, kind: "link" | "door", id: string, open: boolean): Game`
- `setHousingRoomAccess(game: Game, roomId: string, allowedActorIds: string[] | null): Game`

新しい移動指示は `order(game,id,"home-move",JSON.stringify({roomId,cell}))`。対象は有効な床。UIは部屋の入口と人物の現在地点へ移動する選択肢を出す。設備は既存need/work:cook指示から選び、本人の実位置から届く空き枠のうち、移動＋利用の最短、同値は安定したslot ID順とする。

## 3. 行動、時間、材料

新方式のhome needは設備の基本利用時間（basinは水場往復の既存値を加える）をuseMinutesとする。cookは既存の技能・気分・負傷補正後の料理時間に、設備time-10を加える。古いservice/cookingStationの移動込みminutesを再利用しない。

Task.total/remainingはuseの利用時間を保持し、Task.remainingを別時計として減らさない。moveの表示値は現在の経路見積りに追従できるが、状態を進める根拠にしない。時計、進捗、実位置の本体はSpatialState。`use-completed`で一回だけ既存finishを呼ぶ。move完了は移動として扱う。取消イベントは効果を出さず予約返却のみ。

同一点の指示、到着分の利用消費、区間途中の取消はH1-A契約どおり。取消時に区間の途中ならTaskを残し、現在区間の退出後に返却・解除を一回行う。新指示での置換は停止地点なら試行用clone上で取消→計画→受理を行い、失敗なら元Taskと材料を保持する。移動中の別指示は元指示を壊さず、先に取消して退出を待つ理由を表示する。

旧Taskはspatialなしで旧時間・予約のまま完了/取消する。旧作業が使う設備や接続を壊す編集は、作業が終わるまで拒否する。旧原本の継続は旧規則の結果を維持する。新方式の分岐では、旧の未確定位置を新しい同席・共食の根拠にしない。

旧の設備作業には経路の記録がないため、分岐時に現在の部屋から設備の部屋までの決定的な最短link列を、互換継続用の保護対象としてlegacyStationPathsへ保存する。これは過去の実経路や進行段階を復元したものではない。作業中はこの列の接続を撤去できないが、列を残した近道の追加は許す。追加→保存再開→旧接続撤去でも保護対象を再計算して取り替えない。作業完了・取消・置換時にその人物の保護記録を除く。検証は参照人物・旧設備Task・連続した部屋間経路の整合を確認する。

新方式の自宅で新しい会話・手当て等を始めるには、双方が実際に同じ地点で待機できること。相手のroomを書き換えて成立させない。地域・野外の組行動の全面移植は後続。新方式の共食加点は、実際に同じ使用位置で両者がhunger利用を重ねた1分以上をTask.spatial.mealPartnersに記録し、各自の完了時に各自へ一回だけ適用する。移動・待機・取消・旧未確定Taskを参加時間へ数えない。

社交設備の新しい利用は、指示時に目的地にいた相手だけで会話の効果を決めない。本人が利用時間を1分消費し、相手もその1分の開始・終了に同じ地点にいたことを観測した場合に限り、Task.spatial.socialCompanyへtrueを記録する。到着だけ、通過、地域への出発、未確定位置は同席に数えない。記録は途中保存で保持し、完了時の効果・声の記憶・表示に使う。観測なしは手紙として扱い、旧の空間接続なしTaskは従来の結果を維持する。現在は同席の有無を記録し、交流時間に比例する効果は後続で設計する。

自主会話・手当ての相手候補にも現在の地点と実行条件を適用し、先に並ぶ別室の相手が、後に並ぶ実行可能な相手を隠さないようにする。有効候補間の優先順と、旧方式・屋外の互換規則は保つ。屋外の挿絵には実際の相互参照を持つ組行動の相手を表示できるが、同じ地域名だけでは同席を確定しない。

## 4. 間取り変更、理由と再開

編集は先に新しいtopologyを構築し、現在マス、移動の着地、進入中接続、予約された家具と使用位置、旧作業の参照を照合する。不成立なら木材・時計・家・runtimeを全て保持する。無関係な編集と、将来通る経路の変更は許し、受理済み作業は条件に応じて待機する。

閉鎖や許可変更自体は時計を進めない。進入済みの区間は終点まで進み、次の進行で新条件を確認する。開放・許可の復旧後は同じ作業・残り利用時間・材料予約で再試行する。UIに未実装のバックログを示す「再開」ボタンは作らない。待機理由と対処を表示し、通常の時間進行で再評価する。

部屋の許可は新規の入室と設備利用を制限する。すでに室内にいる人は許可を外されても室内歩行と退室ができ、一度出たら再入室はできない。したがってentryRulesは設定上の許可人物に、その部屋に実在する人物（移動中は進入済み区間の出発側）を加えて導出し、位置が変わる各分の境界で更新する。設備slotの許可にはこの退室用の例外を加えない。物理的に戸を閉じた場合は通常の閉鎖として扱う。

次の完了は、使用残時間だけをminにしない。移動残り＋再計算した残経路＋利用時間、取消の退出時間、旧Taskの残りを使う。完了を見積もれない待機しかなければボタンを無効にして理由を示す。

## 5. 保存と互換性

- 新しい `LIBRARY_KEY = "yohaku-reform-library-v2"`、Library.format=2。旧キー `yohaku-reform-library-v1` は変更しない。
- 新キーが存在すればそれを優先し、不正な新保存から旧保存へ黙って戻らない。新キーがないときだけ旧手帳を読み取り、format2の手帳へ複写して使う。複写の説明を出す。
- 書込み候補は名前の正規化・分岐・複製を終えた実際のJSONを、setItemより先に読戻し検証する。不正な候補は原本の破損・容量不足と区別して拒否し、既存の全枠・旧新キー・表示中の暮らしを保つ。旧作業の設備席等を忠実に変換できない場合は、現在状態と最初の朝のどちらが原因かを示して分岐だけを拒否する。架空の席や新しい作業時間へ置き換えず、元の旧方式は引き続き利用できる。
- 初回複写では旧rawも競合の照合値として保持し、最初の新キー書込みまでに旧保存が変われば操作を中断して最新へ切り替える。新キーの別タブ更新・削除・不正JSONでも上書きしない。
- `localStorage`の読取りと書込みには一体の排他保証がない。同期の`writeLocal`は照合と書込みを担い、画面は非同期の`writeLocalCoordinated`を通す。Web Locksがある環境では`yohaku-reform-library-v2:write`の排他ロック内で照合から書込みまで実行し、同じ新版のタブ間で順番をそろえる。APIがない環境では直前照合へ戻し、複数タブで同時操作しない案内を示す。ロック取得が失敗した場合は保存不可として返し、黙って排他なしの書込みへ切り替えない。これは協調する新版タブ間の保護であり、旧コードや外部の保存編集までロックするものではない。
- export envelopeはhousingを含む場合version2。housingのない旧slotはversion1の書出しを維持する。version1の包みへhousingを混入した入力は拒否する。
- `upgradeHousingSlot(slot,name)` は新しいIDへ分岐し、game/originにそれぞれlegacy runtimeを作る。元slotも元キーも保持する。通常の分岐は元のモードを引き継ぐ。
- 検証は既存Game検証＋SpatialState検証＋相互照合。時計、人物の分割、地点とroom、地形、control、Task/order/slot/reservation、利用残時間、共食記録の参照・値を確認する。片方のoriginだけ不正でもslot全体を拒否する。
- 完了済みの仕事を取消→再登録して復活させない。保存/読込みはbeginを呼ばず、材料を再確保しない。

## 6. UIと試遊

人物作成の内容を変えず、新規の暮らしは新方式で開始する。旧暮らしには「住居の移動を使う暮らしに分岐」を用意し、旧作業の互換継続と入口初期化を説明する。生活画面は誰の指示か、現在地/移動区間、行き先、移動/利用/待機/取消/旧作業の区別、利用残り、予約材料と取消の扱いを示す。

住居パネルに部屋へ移動、近くへ移動、部屋間通路・室内戸の開閉、部屋を利用できる人物の設定を置く。各操作は実行前と同じ判定から不可理由を返す。家の編集画面の旧入口基準の見積りを、本人の実位置からの見積りと混同させない。

試遊は新規人物作成→設備指示→移動中→途中保存→再読込み→利用完了、旧途中作業からの分岐、通路閉鎖待機→開放→継続、途中取消→予約返却、別タブ競合、長い表示と320/390/PC幅。実機・Safariの確認とは区別する。
