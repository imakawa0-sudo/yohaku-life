# H5a：一室の寒さ対策

## 目的と位置付け

寝室で休む時間、居間で食事や交流をする時間、外へ働きに出る時間を、同じ人物・時計・位置・材料の上で選べるようにする。H5aでは室温の数値計算を新設せず、既存の初霜と寒さによる休息消耗に、部屋ごとの対策を結び付ける。

この設計は、継続開発の依頼と前回のH5a候補に基づく今回の開発判断である。材料量・所要時間・画面の細部を、ユーザーが個別に承認した仕様とは記録しない。GitHub main `4ef04e6d8da645ecdd05aee28eae1262057804d7` と一致するコードを基準にする。変更前テストは1091件成功。

## 比較した案

| 案 | 利点 | 採否と理由 |
| --- | --- | --- |
| クリックで即座に部屋を保温 | 小さく実装できる | 不採用。時間・人物の所在・材料運搬が結び付かない |
| 新しい独立した工事タスクを追加 | 一室専用の短い導線を作れる | 不採用。取消・担当交代・材料返却・保存を別に実装する必要がある |
| 既存の増築工事に寒さ対策の種別を追加 | 運搬・施工・引継ぎ・回収・保存を共用できる | 採用。工事完了記録から対象室の効果を導出する |

## 遊び方

1. 「住まい」で「一室の寒さ対策」を開き、部屋と室内の仮置き床を選ぶ。
2. 計画を作る。計画・選択だけでは時計も木材も変わらない。
3. 木材1を共同備蓄から取り置く。
4. 住人へ搬入を指示する。移動・運搬は既存の経路、通行・入室許可、所要時間に従う。
5. 届いた木材の場所で施工を合計30分行う。技能制限はない。途中で担当を外し、別の住人に残りを任せられる。
6. 30分の施工完了時に、既存の増築と同じ経路で完成を自動反映する。その時点で材料を一度だけ消費し、次の1分から部屋の対策が有効になる。完成反映が保留された場合の既存の再試行操作は残す。

中止時は既存の工事と同様、運搬中なら区間の終点で解除する。持ち出した木材は供給口へ運び戻して回収する。途中の作業時間・材料・予約・所在を保存し、再読込で続けられる。

## 効果と境界

- 初霜以降、対策済みの部屋に実際にいる住人は寒さによる休息消耗の上乗せを受けない。通常の消耗、移動の負担、欲求行動の補正は従来どおり。
- 未対策では寒さの上乗せは通常体質1.2倍、寒さに弱い体質1.6倍。今回はこの係数を変更しない。
- その1分の開始位置で判定する。到着した瞬間に、移動していた1分全体の効果をさかのぼって変えない。移動中の地点は既存の `housingSourcePoint` に従う。
- 目的室、予約した寝床、`Task.room` を現在地として使わない。外出・地域移動中・住居内の位置が未確定の住人に、一室の対策は適用しない。
- 施工中は未対策。完成反映後の時間から有効。部屋の名前変更・家具の変更・同じ部屋の広さ変更で効果を失わせない（今回は面積比例の断熱費ではない）。
- 現行モデルでは初期の `yard` が屋外、他の部屋が屋内。表示名では判定しない。裏庭は対象外。将来の屋根・屋外区画の設計をこの区分に固定しない。
- 既存の `wood:master` は木材3と技能5または木工専門化で行う家全体の断熱雨戸として残す。従来の自宅範囲（裏庭を含む）への効果を維持する。地域移動中に出発地が自宅のまま残るため防寒が漏れる問題は、住居の移動を使うゲームでは所在判定により防ぐ。
- 家全体の対策が済んでいれば新しい一室対策の計画は不要として禁止する。既存の一室工事や完成履歴は破棄しない。全体工事が並行して終わっても、既存の一室工事は完了または取消・回収できる。
- 増築と寒さ対策を合わせて未解決の工事は1件。別種類に変えて同じ材料・工事場所を二重使用できない。

## 保存と実装の境界

- `RoomConstruction` に任意の `kind?: "insulation"` を追加する。省略は従来の増築であり、古い保存をそのまま受け付ける。明示的な未知値や `undefined` は保存検証で拒否する。
- 寒さ対策の対象は `neighborId`。仮置き場所は必ずその部屋で、居間の供給口とは異なる歩ける床とする。
- 必要木材は増築6、寒さ対策1。`requiredWood` と実際の材料量を種別別に検証する。共通処理の引落・返却・表示は計画の値に従う。
- 完成時の `roomId` は増築では新しい部屋、寒さ対策では対象の既存部屋。寒さ対策は部屋数、間取り、`house.nextId` を変えない。
- 部屋の対策済み状態は、保持される工事履歴の `kind === "insulation" && status === "completed"` から導出する。重複した `insulatedRooms` 状態は保存しない。
- 保存検証では、対象室の存在・屋外除外・二重完成や完成後の再計画禁止・材料量・工事担当・空間予約・時刻を検証する。増築済み部屋列の照合には増築だけを含める。後の増築で作られた部屋を先に保温した履歴は拒否する。完成・回収済みの過去の仮置き床は、その後の正当な模様替えを妨げない。
- `housing/insulation.ts` に計画用入口と対策状態・寒さの所在判定をまとめる。既存の循環依存を増やさないよう、計画作成は共通のconstruction処理を利用し、型参照にはtype importを使う。

## 画面

- 新しい「一室の寒さ対策」パネルに必要木材・施工時間・対象室の状態を表示する。裏庭が対象外であること、移動・外出では別の場所の効果を受けないことを短く説明する。木材不足でも計画は作成でき、取り置く操作にだけ必要量を求める。
- 寒さ対策と増築は共通の工事カードを使う。カードの作業名、予約量、履歴は工事の種類に合う言葉にする。同じ工事カードを2か所へ重複表示しない。
- 既存の増築フォーム・人物作成・4タブ・時刻操作・PC14px/スマートフォン13pxを維持する。
- 初霜後の生活画面で、選択中の人物が受けている対策または未対策の疲れやすさを示す。温度、病気、火事、死亡など未実装の作用は表示しない。

## 検証

実エンジンで材料1の引落と回収、搬入、施工30分、中断と交代、完成の一度限りの反映、保存の続行一致を確認する。初霜前後、通常/寒さに弱い体質、寝室/居間/裏庭/外出、到着直前の1分、目的室だけの予約、家全体の対策との共存を比較する。古い増築と保存検証を壊していないことを既存テストで確かめる。

ビルド済み単体HTMLをPCとスマートフォン幅で操作する。通常の新規開始からの経路と、初霜の境界用に制御した保存からの経路を区別して記録する。標準Playwrightコマンドが環境で起動不能なら、その結果を明示し、管理されたブラウザで同じHTMLの操作を試す。試遊できなかった経路は確認済みと報告しない。
