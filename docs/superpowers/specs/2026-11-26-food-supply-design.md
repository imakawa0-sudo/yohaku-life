# H6b：一束の補充担当

2026-11-26 Asia/Taipei。H6a後の次工程。仕様判断は開発側の判断であり、個別案をユーザーが指定・承認したという意味ではない。継続開発、単体HTML試遊、GitHub main一関連コミットとNotionへの保存は既存の依頼に含まれる。

## 目的と現在の問題

一束を取り分け、床へ運び、料理に使うH6aの物理的な流れを保ったまま、同じ準備を毎回頼む負担を減らす。料理の開始、使う設備、保管場所を決める余地は残す。

実装前の制御比較では、基本料理3回の作業自体は全条件105分。近い保管床・近いかまどの場合、共有在庫107分/料理指示3回、本人準備125分/指示9回、仲間へ都度依頼131分/主指示9回に取消2回（実験用待機5回）だった。仲間の現在行動終了を待つ条件は156分/主指示9回（実験用待機10回）。14条件で食事7→19、食材6→0、360回の保存継続チェック。これらは制御条件の数値であり、一般的な速度保証やUIクリック数ではない。

通常開始の実画面でも、一束消費後に住まいへ戻ると保管部屋・床が未選択となり、取り分けと運搬担当を再指定する必要があった。利点の目標は「速くする」ではなく、同じ担当・置き場の指示を繰り返さずに済むこと。

## Approaches

| 案 | 効果 | 判断 |
| --- | --- | --- |
| 取り分けと運搬を単発指示にまとめる | 一回の手順が短く、実装も小さい | 毎回の依頼が残るため今回は見送る |
| 一束の準備・運搬を指定住人に継続して任せる | 同じ置き場・担当を保存でき、調理と分担は残る | 採用。生活・直接指示・停止理由を同時に扱う |
| 完成料理を目標在庫まで連続生産する | 調理開始も省略できる | 料理・食事・補充・上限が同時に絡むため後段へ |

今回は一つの補充担当、一つの保管床、現物一束（食材2）に限定する。複数束、運搬の予約待ち行列、食品腐敗、冷蔵、所有権、収納家具の効果、自動調理、最適なついで運搬は含めない。

## プレイヤーから見た動き

住まいの食材欄に「一束の補充を任せる」を設け、補充担当・補充先の部屋と床を選ぶ。設定操作は時間を進めず、食材も動かさない。時計を進めると、条件の整った指定住人が共同備蓄から食材2を一束にして運ぶ。

一束が保管中・料理中・別の人の運搬中なら追加で取り分けない。料理に使い終え、担当者の手が空いた後に次の一束を準備する。配送中や調理中も他の住人は通常通り生活する。

方針の「一時停止」は次の補充を止め、進行中の運搬は終える。「再開」で保存した担当と床を使う。「担当を解除」は設定を消すが進行中の運搬は終える。進行中の運搬自体は既存の取消操作で止める。自動補充の運搬を明示的に取り消したときは、即座の取り直しを避けるため補充方針も一時停止する。

直接の別行動を指示した場合は、その有効な指示を優先し、補充方針は保持する。通路の途中から別行動を開始できない既存の安全な区間退出ルールは維持する。無効な指示で進行中の運搬・予約・方針を失わない。

「供給口へ戻す」は返却指示を受け付けた時点、「備蓄に戻す」は在庫への返却が成功した時点で補充方針を一時停止する。返却運搬を途中で取り消しても停止状態を保ち、明示的な再開があるまで運び直さない。戻した直後に再び取り分ける往復を防ぐ。失敗した操作は方針も変えない。

設計確認で返却時の停止時点が曖昧と指摘されたため、上記の受付時停止を採用した。返却を取り消しても補充再開を別に選ぶ必要があることが、この判断の代償である。

## 保存と状態

`HousingRuntime.foodSupply?` を `foodLogistics` と独立した任意項目として持つ。

```ts
type FoodSupplyPolicy = {
  version: 1;
  actorId: string;
  storage: SpatialPoint;
  enabled: boolean;
};
```

一束の台帳は現行version 1を保ち、補充方針を台帳の作り直しで消さない。古い保存には方針を注入しない。設定だけでは台帳や現物を新設しない。読込・再読込・書出しも仕事を開始せず、次の時間進行が開始点になる。

保存は未知キー、型違い、存在しない住人、供給口と同じ床、歩けない/存在しない保管床を拒否する。停止中も設定した床と供給口は有効である必要がある。方針がある間、その床を失う改築は理由つきで拒否し、「担当を解除」後は現物や他の予約の既存制約に従う。

方針がなくても、既に始めた自動運搬は完了・保存できる。食材Taskの `mode: "auto"` は `home-haul` かつ一束割当 `kind: "store"` に限り認める。料理・返却は従来の `direct` 限定。Task、空のreserved、現物、人物、運搬命令の相互照合は緩めない。

## 開始条件と優先順位

既存の危険回避、重傷回復、欲求回復、気分回復、食事備蓄、夜の休息より後、通常の担当仕事・好みの仕事より前で、手が空いた指定住人だけを候補にする。既存の進行中Taskを補充のために中断しない。

補充の追加条件：自宅、危険なし、負傷50未満、全欲求42以上、気分25以上、日中（既存と同じ一日420分以上1180分未満）。これらを満たさない間は待ち、遠隔地から材料を動かさない。予約中の仲間を奪わない。

現物がないときは、共同備蓄2以上・発行番号が安全整数・供給口から保管床までの権限と経路・本人から拾う地点までの経路を確認し、取り分けと運搬割当を原子的に行う。途中で失敗したら、食材・台帳・Task・位置・予約はすべて開始前のまま。

担当のない現物があり、方針と同じ保管床を持ち、まだその床に到着していない場合は、その現物の運搬を再開できる。床が異なる現物は変更せず、今の一束がなくなるまで待つ。保管床にある一束、他の割当中の一束は触らない。

扉が閉じたため開始できない場合は材料を取り分けず待つ。開始後の閉鎖・権限喪失・危険・負傷はH6aの安全な待機/取消/現物保持を使う。料理の出力上限で一束が残った場合も追加作成しない。

毎分の自律判断内で `Game` 全体や `actors` 配列を置換しない。既存人物オブジェクトの参照を保ち、成功した食品・住居・当該Taskの変更だけを採用する。人物の処理順や別作業の成果を失わない。

## 画面

現在の担当、保管床、継続中/一時停止、運搬中/保管済み/開始可能/待機理由を表示する。「手が空くのを待つ」「帰宅を待つ」「生活の用事を優先」「日中を待つ」「食材2が必要」「通路/権限」「別の一束を使用中」など、次に何をすればよいか分かる文にする。内部IDや実装用の状態名を見せない。

設定時は作業中・外出中の住人も選べる。いま運べることと担当を予約することを区別する。入力失敗と保存失敗は明示し、失敗した変更を成功表示しない。タブの切替は時計を動かさず、確定した方針は保存から表示する。自動運搬は「自主行動」として既存人物欄にも現れる。

現行の共同備蓄からの料理、手動取り分け/運搬、材料・設備の明示選択を維持する。今回の政策は自動調理や料理材料の自動切替ではない。

## 検証と完了条件

意味のある境界試験：設定の無時間/無消費、原子的開始、3回補充、同時には一束、busy/direct/急務/夜間/外出/負傷/気分、手動束の扱い、取消/返却での停止、無効指示の保持、途中停止/解除と保存、閉鎖/権限、上限、改築、古い保存と不正保存、他人物の同時作業。

現行の14条件比較を土台に、同じ人物・配置で新担当の繰返しを測る。料理の作業時間、完成時間、準備指示数、待機制御、他の仕事、材料/成果を分ける。速さの改善は測定できた場合だけ記載する。

全テストとビルド後、最新単体HTMLで通常開始→補充担当設定→時計進行→一束料理→次の補充、直接命令、停止/再開、保存再読込、狭い画面を実際に操作する。修正が出たらビルドし直して該当箇所を再試遊する。同じHTMLを成果物にする。

既存1133テストは実装前に全件成功。標準tsxラッパーのIPC制約には既存の `node --import tsx --test tests/*.test.ts` を使う。CLI Chromiumの既知の欠落は管理Chromeで補う。実機や全ブラウザでの検証済みとは扱わない。

## 開発側が引き受ける細部
